# 系統A二層監視 受け入れ確認

## 目的

高頻度セッションが、確認開始から5秒ごとに次回再読込を予約し、未検知なら1分間継続して期限切れになることを確認する。あわせて、在庫更新を想定したDOM変化を検知して停止する経路を独立して確認する。Gmail・外部拡張通知および通常サイトの在庫判定精度は対象外とする。

## 実行

Chrome 120以上で拡張を再読み込みし、テストタブの「A: 受け入れ確認」から各シナリオを実行する。終了するまでテストタブと作成された監視タブを閉じない。

1. 「高頻度・単一URL 継続/期限」を実行する。
   - 1 URLを約1分間監視する。結果カードの確認回数が2回以上となり、「5秒基準で再読込を予約」と「未検知URLを継続・時間満了」が成功してから合格となる。
2. 「高頻度・単一URL 変化検知」を実行する。
   - 初回は未検知、次回確認で在庫更新を想定したテストDOMへ変化し、検知・停止する。
3. 「高頻度・複数URL 継続/期限」を実行する。
   - 2 URLをともに約1分間監視し、両方の時間満了を待って合格となる。
4. 「高頻度・複数URL 変化検知」を実行する。
   - 1件目は次回確認で検知・停止し、2件目は約1分間継続して期限切れになる。両方の結果がそろうまで合格にしない。
5. 「長期・単一URL」を実行する。
   - 基準保存後も最初の30秒アラーム発火まで監視が継続することを確認する。専用アラームの作成・少なくとも1回の発火・停止・設定復元を確認する。

高頻度の「5秒」は、DOM確認を開始した時刻から次回ページ再読込を予約するまでの間隔である。保存処理の時間はこの間隔へ追加しない。ページ読込時間のため、実際の次回DOM確認開始時刻は5秒を超えることがある。

## 判定境界

結果カードでは、セッション作成、対象タブ、初回未検知、監視間隔での再読込予約、該当する検知停止または継続・時間満了、B/Cアラーム分離、設定復元を表示する。旧generation報告の無視は、Content Scriptが報告する高頻度セッションだけの確認項目であり、`chrome.alarms` が直接確認する長期セッションでは対象外とする。

- 継続/期限シナリオは、1分より前に検知・停止した場合は不合格とする。
- 変化検知シナリオのDOM変更は、在庫が更新された場面を想定したテスト専用の再現である。通常監視では実行しない。
- `tab_missing`、セレクタエラー、想定外停止、必須項目の未達は不合格とする。
- 合格は通常運用サイトの検知精度、通知送信、対象タブを閉じた後の高頻度継続を保証しない。

## 補助確認

長期・単一URLでは、次の手順で拡張機能再読み込み後の復元も確認できる。現行Chromeには拡張機能Service Workerだけを手動停止する画面がないため、DevToolsの「Service workers」は使用しない。

1. 「長期・単一URL」を開始し、`✅ 基準ダウンロード完了` を確認する。監視タブは開いたままにする。
2. 30秒アラーム発火前にpopupとService Worker DevToolsを閉じ、`chrome://extensions` のPageRecorderカードで ↻（再読み込み）を押す。
3. popupを開き直す。結果カードは再読み込み前の実行状態を表示し続ける。
4. `Service Worker初期化完了` の後、`🔄 [二層監視テスト] Service Worker再起動後に長期セッションを復元`、アラームによるDOM変更・検知・停止を確認する。結果カードの「Service Worker再起動後に復元」が成功となり、最終判定が `status: 'passed'` なら合格とする。

必要に応じて `chrome.storage.local` の `singleMonitoringSessions` を確認し、停止時に `active: false` が先に保存されることも確認する。

## tab消失時の安全停止

長期・単一URLでは、基準保存後から初回アラーム発火まで約30秒間、次の手順で確認できる。

1. 「長期・単一URL」を開始し、`✅ 基準ダウンロード完了` を確認する。
2. `✅ 二層監視テスト判定完了` が出ていないことを確認して、作成された監視タブを閉じる。
3. Service Worker Console で `stopReason: 'tab_removed'` と `active: false` を確認する。
4. `singleMonitoringSessions` の対象セッションが `active: false` であり、専用アラームが削除されていることを確認する。

この確認は受け入れテストの合格判定を目的としない。tabを閉じたため、最終結果は `tab_removed` による不合格となる。

## 高頻度セッションのtab消失時安全停止

高頻度・単一URLでも、対象tabを閉じた場合に保存済みセッションを安全に停止することを確認する。この確認は受け入れテストの合格判定を目的としない。

1. popup の「単一URL監視」を開き、監視方式を「高頻度セッション」、監視間隔を20秒、監視時間を1分にする。監視開始時の即座検知はOFFにする。
2. 対象URL・セレクタ・キーワードを設定し、「開始」を押す。作成された監視tabが開いたことを確認する。
3. 基準ダウンロード完了を待たず、監視tabを閉じる。
4. Service Worker Console で `stopReason: 'tab_removed'` と `active: false` を確認する。
5. `singleMonitoringSessions` の対象セッションが `active: false` となり、対象の `singleMonitoringSession_` アラームだけが解除されたことを確認する。

テストタブの「テスト開始（自動判定）」も本番と同じ二層セッションで動くが、本番設定の退避・復元と自動判定を伴うため、このtab消失確認には通常の「開始」を使う。通常監視には結果カードがないため、ConsoleとStorageを判定根拠にする。定時監視の `dailyStockCheck_` および `stockWatchTick_` アラームは停止対象ではない。

## 高頻度・複数URLで片方を閉じた場合

複数URL監視では、2件とも検知しない状態で開始する。対象ごとのキーワードをページに存在しない一時値（例: `__tab_removed_test__`）へ設定し、監視開始時の即座検知はOFFにする。検知済みの対象は `detected` で停止するため、この確認には使えない。

1. 「複数URL監視」で2件を高頻度・20秒・1分に設定し、「全て開始」を押す。
2. 2件の `単一監視開始処理開始` を確認し、どちらにも `detected` 停止が出ていないことを確認する。
3. 片方の監視tabだけを閉じる。
4. 閉じたtabだけが `stopReason: 'tab_removed'`・`active: false` となり、もう一方はactiveのまま監視を継続することを確認する。
5. 確認後は「全て停止」を押し、一時キーワードを元の設定へ戻す。
