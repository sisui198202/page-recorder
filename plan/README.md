# プロジェクト構成ルール

## 目的
ドキュメントと計画を分離し、可読性・保守性・実行力を高める

---

## ディレクトリ構成

```
/
├── PRD/           # 設計・要件（正本）
├── plan/          # 計画・改善
│   ├── docs/      # 改善計画・戦略
│   └── todo.md    # 実行タスク
├── docs/
│   └── 実装済/   # 完了した計画・実装メモの保管
```

---

## PRD/ の役割（事実）

以下の内容のみを格納する：

- 仕様書
- 技術メモ
- 調査結果
- 実装の現状
- API仕様
- エラー事例

### 原則
- 「未来（改善・計画）」は書かない
- 現在の状態・事実のみを書く

---

## plan/docs/ の役割（計画）

以下の内容のみを格納する：

- 改善計画
- 優先順位付き方針
- ロードマップ
- リファクタリング案
- 設計改善

### 原則
- 「どうするか」を書く
- 「なぜやるか」も必ず書く

---

## plan/todo.md の役割（実行）

計画を実行可能なタスクに分解する

### 運用上の優先関係

- `plan/README.md` を `plan/` 配下の全体ルールの正本とする
- `plan/docs/README.md` は `plan/docs/` 内の補足ルールとして扱い、全体ルールと矛盾しない範囲で読む
- 新タスク化の判断は、原則として `plan/todo.md` を優先し、必要に応じて `plan/docs/` の優先順や背景説明で補う

---

## 情報の流れ

```
PRD（調査・事実）
  ↓
plan/docs（改善計画）
  ↓
plan/todo.md（タスク化）
  ↓
実装
```

## 命名ルール

### PRD/
- ○○仕様.md
- ○○調査.md
- ○○メモ.md

### plan/docs/
- 優先順位つき改善計画書.md
- ○○改善案.md
- ○○ロードマップ.md

---

## 更新ルール

- PRD → 事実が変わったとき更新
- plan → 方針が変わったとき更新
- todo → 常に最新状態を維持
- docs/実装済 → 完了済みの計画・実装記録を保管

---

## 完了タスクの扱い

- `.steering/done/` を完了タスクの実行履歴の正本とする
- `plan/todo.md` の終端状態（`[x]`・`[-]`・`[/]`）は、対応記録を確認後に削除する
- `plan/docs/` を起点にした task は、実装・必要な自動/手動テスト・`.steering/done/` への完了記録がそろったら、対応計画ファイルを必ず `docs/実装済/` へ移動する
- `.steering/` の実装履歴は `.steering/done/` と `done.md` で管理する
- `task-close` 前に `ai-notes.md` の更新要否を確認し、必要な知見を含めた状態で `.steering/done/` へ保持する
- 「残タスク」がある場合は未完了として残すか、新規タスクに分割

### 完了時の基本ルール

- `plan/todo.md` は「未着手/進行中のみ」を置く
- 完了済みの実行履歴は `.steering/done/` に残す
- 完了済みの計画・実装記録は `docs/実装済/` に残す
- `plan/docs/` に残すのは未完了の計画、継続中の改善案、または将来の方針のみ
- 1つの計画書に未完了項目と完了項目が混在する場合は、完了部分を `docs/実装済/` に分離し、未完了部分だけを残す

### `task-close` の最終ゲート

- `plan/todo.md` があるリポジトリでは、plan 整理直後かつ commit 前に `npm run check:plan-todo` を実行する
- 検査で終端状態が検出された場合は、commit・merge・`.steering/done/` への移動を中断し、対応記録の確認後に該当項目を削除する

### `plan/todo.md` 変更時の必須ゲート

- `plan/todo.md` を変更した場合は、作業種別や `task-close` の有無にかかわらず、最終報告前に `npm run check:plan-todo` を実行する
- `[x]`・`[-]`・`[/]` が検出された場合は、対応記録を確認して該当項目全体を削除し、検査が成功するまで完了報告しない
- 終端項目が既存差分に含まれていても、完了記録を確認できれば削除する。既存変更を保持することは、終端状態を残す理由にしない

### `docs/` と `docs/実装済/` の判断ルール

- `docs/` には、現在も正本として参照し続ける説明・設計方針・運用メモを置く
- `docs/実装済/` には、完了した計画・実装記録・履歴として残す成果物説明を置く
- 「今後も更新し続ける文書」は `docs/`、「完了時点の記録として残す文書」は `docs/実装済/` を優先する

### 完了前のルール更新提案チェック

- `task-close` 前後では、今回の実装・docs整理・完了処理の中で新しい判断基準を言語化したか確認する
- 同時に、`ai-notes.md` に close 前の引き継ぎ整理や再利用知見を書き残す必要があるか確認する
- 次のいずれかに当てはまる場合は「ルール化候補」として確認する
  - 会話中に「ルールにした方がよい」と判断した
  - ドキュメント配置、完了処理、命名、責務分離など再発しやすい運用判断が出た
  - 既存ルールだけでは判断できず、その場で新しい基準を言語化した
  - 同種の迷いが2回以上出た、または1回でも影響範囲が広い
- 次のものは原則として候補にしない
  - 単発のローカル事情
  - プロジェクト固有の一時対応
  - 設計未確定で今後変わり得るもの
- 候補が出たら、次の順で既存ルールと適用範囲を確認する
  1. repo ローカルルール (`AGENTS.md` / `CLAUDE.md` / `README.md` / `plan/README.md` / 必要時 `rules/`)
  2. `~/.claude/rules/` の正本
  3. `~/.codex/rules/` の追従要約
  4. `~/Dropbox/Rule/Category` の汎用正本
- 既存ルールで明文化済みなら更新しない
- repo 固有の判断なら repo ローカルだけ更新し、複数 repo で再利用する判断なら Claude / Codex / Dropbox まで提案対象に含める
- `done.md` または最終報告には、ルール更新提案の有無・候補ファイル・更新範囲・更新しない理由を残す

### ルール化 skill の使い分け

- repo 内で再利用知見を残すときは `knowledge-universal`
- 知見をルール化候補へ変換するときは `knowledge-auto-rule`
- ルール層と知識層の整合確認は `sync-rule-knowledge`

## PRD/ideas/ の役割（アイデア）

未熟成のアイデア候補を保管する

### 原則
- 「やるかどうか未定」の段階で記録
- 採用決定後に plan/docs/ へ移行

### 命名ルール
- YYMMDD-アイデア名.md

---

## タスク実行フロー

```
PRD/ideas/（未熟成・候補）
    ↓ 採用判断
plan/docs/（計画化・戦略）
    ↓ 分解
plan/todo.md（実行タスク）
    ↓ 選択
/newtask {タスク名}
    ↓
.steering/YYMMDD-HHmm_{タスク名}/
├── requirements.md
├── design.md
├── tasks.md
└── ai-notes.md
    ↓ 実装完了
docs/実装済/ または .steering/done/
```

### `/newtask` 起点の補足

- 通常は `plan/todo.md` に載った項目を選んで `/newtask` する
- まだ `plan/todo.md` に載っていない計画を `plan/docs/` から直接起票する場合は、起票理由と起点文書を `requirements.md` に残す
- 実装完了後は、`plan/todo.md` と `plan/docs/` の両方を整理対象として扱う
- `.steering/<task>/` では `requirements.md > design.md > tasks.md > ai-notes.md` の順で参照する
- `ai-notes.md` は回数基準ではなくイベント基準で更新する
- 更新トリガーは、重要な実装判断、不採用パターン確定、ユーザーの手動テスト成功/失敗報告、`task-close` 前の引き継ぎ整理とする
- `decisions.md` は判断理由、`ai-notes.md` は実務知見、`done.md` は完了要約として分けて扱う

### 粒度の関係

| 場所 | 粒度 | 例 |
|-----|------|-----|
| PRD/ideas/ | アイデア | 「○○機能があると便利」 |
| plan/docs/ | 戦略 | 「F3にローマ字検索導入」 |
| plan/todo.md | タスク | チェックリスト形式 |
| .steering/ | 実行 | 具体的な実装手順 |
