## 🎯 目的

design.md に基づいた実装タスクを管理する。
通常開発を基本とし、DOM操作・Playwright・Chrome拡張が関わる場合のみ条件付きPhaseを使用する。

---

<a id="scope"></a>

## 🧩 実装対象

- design.md に記載された内容のみ実装する
- 未記載仕様は実装しない
- requirements.md / design.md / tasks.md の整合性を保つ

---

<a id="status-rules"></a>

## ✅ チェック状態の定義

- [ ] 未着手。今回タスクで対応予定の項目
- [~] 実装済み。実装は完了したが、確認が未完了の項目
- [x] 完了。対象項目について、実装と確認の両方が完了した項目
- [-] 保留。このタスクでは今回対応しないが、再検討・対応余地がある項目
- [/] 却下。今回タスクでは不採用確定の項目

---

<a id="workflow-rules"></a>

## 📋 進め方ルール

- Phase単位で進める
- 各項目は、実行した直後に状態を更新する
- 各Phaseごとに「実装」と「確認」をセットで完了させる
- 実装だけ完了した項目は `[~]` に更新する
- 実装と確認の両方が完了した項目だけを `[x]` に更新する
- 実装完了後にチェックを後回しにしない。対象作業が終わった時点で、その場で `tasks.md` を更新する
- 今回タスクで対応しない項目は、保留なら `[-]`、不採用確定なら `[/]` に更新する
- `[-]` にした項目は、必要に応じて保留理由を差分・課題メモまたは decisions.md に残す
- `[/]` にした項目は、却下理由を差分・課題メモまたは decisions.md に残す
- 各Phaseの終了時に、チェック状態と実際の実装・確認状況が一致しているか見直す
- `tasks.md` の状態と実際の進捗を常に一致させる
- 条件付きPhaseは、該当する場合のみ使用する
- 該当しない条件付きPhaseは削除、`[-]`、または `[/]` で理由を明記する

<a id="definition-of-check"></a>

## 📌 「確認」の定義

- `確認` は、実装した内容が期待通りかを対応する確認項目で確かめること
- `確認` は手動テストだけを指さない
- 内容確認、挙動確認、差分確認、連携確認、完了条件確認も `確認` に含む
- 実装だけ終わった状態は `[~]`
- 実装と確認の両方が完了した状態だけを `[x]` とする

### 例

- `background script の動作を確認する` を実装して設定を直しただけなら `[~]`
- 実際にメッセージ受信やイベント発火を確認できたら `[x]`
- `docs更新要否を確認する` は、更新が必要か不要かを判断できた時点で `[x]`

---

<a id="prohibited"></a>

## 🚨 禁止事項

- design.md にない内容を実装すること
- 未確認のまま次Phaseへ進むこと
- 複数Phaseをまとめて実装すること
- 未完了タスクを完了扱いにすること
- DOM系作業で未検証セレクタを使うこと
- 拡張連携があるのに連携確認を省略すること

# Phase 2: DOM検証（該当時のみ）

> DOM操作・スクレイピング・画面要素取得・セレクタ利用がある場合のみ使用する

- [-] id / data属性 / 構造 / class の優先順位で確認する

## 🧪 手動テスト

- [-] `document.querySelectorAll(selector).length` で件数確認
- [-] `innerText` / `textContent` / `getAttribute()` で取得内容確認
- [-] 想定対象のみ取得できることを確認する

### このPhaseで確認とみなすもの

- 候補セレクタで対象要素を安定して取得できる
- 想定外の要素を拾っていない
- 採用セレクタの根拠を説明できる

### 実例
