# 系統A-MV3監視安定化計画

## 目的

系統A（単一 URL / 複数 URL のキーワード監視）は今後も維持する。用途に応じて、高頻度セッションと長期監視を明示的に選べる二層構成へ移行する。

- 高頻度セッションは、先着検知・自動購入連携を想定し、対象タブの Content Script で短間隔のDOM確認を行う。
- 長期監視は、再入荷待ちを想定し、`chrome.alarms` と永続化した監視状態でMV3休止耐性を確保する。

## 対象と制約

- 対象は系統Aの定期監視だけとする。系統B/Cとの統合、Content Script の廃止、popup全体の再設計は含めない。
- popupで監視モードを明示的に選択する。既存設定にモードがない場合は、高頻度セッションとして扱い、既存の短間隔設定を維持する。
- 高頻度セッションの監視時間は1〜60分、確認間隔は既存どおり5〜20秒程度とする。対象タブ、Chrome、端末が稼働していることを前提とし、スリープ・タブ破棄・Chrome終了時の継続は保証しない。
- 長期監視の監視時間は30分〜8時間、確認間隔は30秒以上とする。アラームは遅延し得るため、正確な時刻実行ではなくベストエフォートの確認契機として扱う。
- 検知結果、通知、外部拡張への連携、baseline保存、停止条件の意味は両モードで共通に保つ。
- 長期監視では、重複実行、停止済み監視の再開、タブ消失時の扱いを既存仕様と整合させる。
- 既存の系統B/C向けアラーム名・状態管理を変更しない。

## 実施方針

別途 `/newtask` を起票し、`requirements → design → tasks → 実装` の順に進める。実装前に以下を確定する。

1. `monitoringMode` を系統A設定に追加し、高頻度セッションと長期監視の入力制約・表示を定義する。
2. 高頻度セッションは、Content Scriptが保存済みのセッション設定を取得して短間隔のDOM確認を再開し、検知結果をbackgroundへ送る経路にする。
3. 長期監視は、監視設定、開始・終了時刻、停止状態、アラーム名を `chrome.storage.local` に保存し、アラーム発火時にbackgroundが状態を復元して確認を行う。
4. Service Worker起動時に保存済みの長期監視とアラームを照合し、不足するアラームを再作成する。停止済みまたは終了済みの監視は復元しない。
5. 両モードのDOM判定後は共通の検知・通知・停止処理へ渡し、検知結果の意味を分岐させない。

実装では特性テストを先行する。高頻度セッションは既存の短間隔運用との互換性を維持し、長期監視だけを永続化・アラーム基盤へ移行する。

## 検証

- 自動: モード別の入力制約、開始、即時判定、定期判定、停止、異常時停止、共通の検知通知を特性テストで固定する。
- 高頻度: 単一URL・複数URLで5〜20秒程度の確認、1〜60分の監視時間、検知後の通知・停止をChrome実機で確認する。タブを閉じた場合は停止することも確認する。
- 長期: 30秒以上の確認間隔、30分〜8時間の監視時間、Service Worker休止・再起動後のアラーム復元、停止済み・終了済み監視が再開しないことを確認する。
- 回帰: セレクタ異常、tab消失、baseline保存、外部拡張通知を両モードで確認する。
