# 🧠 decisions.md

## 🎯 目的

設計・仕様・実装に関する意思決定と、その理由を記録する。

---

## 📌 使い方

- 「なぜそうしたか」を必ず残す
- 後から見て判断理由が分かる状態にする
- 却下案も含めて記録する

## 🧩 Decision一覧

### D-001: 状態遷移判定統一タスクを却下し、ブランチを削除する

- **決定内容**: `261023-1332_multi-site-state-transition`（ブランチ `feature/multi-site-state-transition`、未push・未マージのコミット `4270ccf`・`5cd946c`・`c1d23fc`・`bcab2d4`）を却下し、ブランチを削除する。起点だった `plan/todo.md` の項目「複数サイト監視／旧 `setInterval` 経路を、単一URL監視と同じ状態遷移判定へ統一する」も、本タスクの項目に置き換えて削除する。
- **背景**: そのタスクは、テストタブ専用の旧 `setInterval` 経路の判定を本番にそろえる応急処置だった。本タスクで旧経路そのものを削除する。
- **採用理由**: 削除予定のコードを直しても価値が残らない。判定ロジックの二重保守をなくせる。
- **引き継ぐ知見**: 通常の複数URL監視は `startMultipleMonitoring` 冒頭の分岐で二層セッションへ委譲されている。旧経路を読んで本番の不具合と誤認した経緯は `~/.claude/rules/05_debug/bugfix-operation-rule.md` の NG パターン1に記録済み。
- **ステータス**: 確定（2026-10-23 ユーザー承認「ブランチを削除してよい」）

### D-002: 本番の設定範囲で動かす

- **決定内容**: 全シナリオを高頻度モードの範囲内（間隔5秒・時間60秒）で動かし、`allowTestTiming` を使わない。
- **採用理由**: テストタブの役割は本番に最も近い状態で確かめること。満了シナリオは約60秒かかるが、本番と違う短い時間では本番の動きを保証できない。
- **関連ドキュメント**: design.md
- **ステータス**: 確定（2026-10-23 design承認）

### D-007: 再現の自動・手動をトグルで切り替える

- **決定内容**: popup のトグルで検知の再現を「自動」「手動」に切り替える（既定は自動）。手動のときは、基準取得後の最初の読み込み直しの直後に、テストセッションだけ20秒の受付時間を設け、受付時間中であることと残り秒数をログとテストタブに表示する。判定はどちらも自動。
- **背景**: ユーザーが手動での再現も選べるようにしたい（2026-10-23）。本番の高頻度監視は読み込み直しの直後に確認するため、受付時間がないと手で変えた文言が確認前に消える。
- **採用理由**: `testOnly` 付きのテストセッションだけで動くので、本番の監視の挙動を変えない。20秒はユーザー指定。
- **関連ドキュメント**: requirements.md 要件3、design.md
- **ステータス**: 確定（2026-10-23 design承認）
