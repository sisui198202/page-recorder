# 在庫Fetch一括診断の判定ガイド

## 目的

ECサイトを1件選択して「在庫あり・なしをまとめて診断」を実行すると、登録済みの在庫あり・在庫なしサンプルに対して、Service WorkerのFetch HTMLと表示後DOMを比較する。

在庫ありでは、セレクタに一致した要素内にキーワードがあることを期待する。在庫なしでは、同じセレクタには一致するがキーワードはないことを期待する。

この診断は、現在のセレクタ／キーワードがFetch HTMLでも使える可能性を確認するものであり、セレクタの自動選定や実監視方式の自動変更は行わない。

## 最終判定と次のアクション

| 判定                     | 何が分かるか                                                                                                                                                     | 次のアクション                                                                                                                                                                         |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FETCH_SUPPORTED`        | 登録済みの全サンプルで、Fetch HTMLとDOMの双方が在庫あり・なしの期待どおりになった。現在のセレクタ／キーワードは、Fetchによる在庫検知の候補として利用可能である。 | 保存されたHTMLと`summary.json`を確認する。異なる商品、SKU、バリエーション、ログイン状態でも同じ結果になるか追加で確認し、Fetch方式の監視実装を別タスクで検討する。                     |
| `DOM_ONLY`               | DOMでは在庫あり・なしを区別できるが、Fetch HTMLでは区別できない。JavaScriptで後から描画される情報、または別APIの情報を使っている可能性がある。                   | 現行のDOM監視を維持する。DevToolsのNetworkでFetch/XHRを確認し、在庫API候補と必要なパラメータを調査する。                                                                               |
| `NEEDS_REVIEW`           | FetchまたはDOMの取得失敗、セレクタ不一致、キーワード不一致などにより、期待値を満たさないサンプルがある。                                                         | run配下の状態・URL別`comparison.json`とHTMLを確認する。商品状態、SKU、バリエーション、ログイン状態、セレクタ、キーワードを確認し、必要ならサンプルまたは監視条件を更新して再診断する。 |
| `SAMPLES_NOT_REGISTERED` | 選択サイトに在庫あり・なしの診断用サンプルが登録されていない。判定に必要な比較データがない。                                                                     | 手動確認済みの在庫あり・なしURLをそれぞれ`site_capture`へ追加し、`scripts/sync-stock-fetch-diagnosis-samples.js`で同梱設定を同期してから再実行する。                                   |

## 表示される成功数の読み方

`在庫あり: Fetch 2/2、DOM 2/2`は、在庫ありサンプル2件のうち、Fetch HTMLとDOMの両方で期待値を満たした件数を示す。同様に、`在庫なし: Fetch 1/1、DOM 1/1`は在庫なしサンプル1件の結果を示す。

Fetchの分子とDOMの分子が各状態の件数と一致して初めて、`FETCH_SUPPORTED`になる。

## `FETCH_SUPPORTED`の扱い

`FETCH_SUPPORTED`は「今回検証したサンプル範囲では、Fetch HTMLで現在の監視条件を使える」という確認結果である。以下は、この診断だけでは確定しない。

- すべての商品・SKU・バリエーションで同じ条件が成立すること
- ログイン状態やサイト改修後も継続して成立すること
- 現行のDOM監視をFetch監視へ置き換えること

Fetch方式を採用する場合は、保存成果物を基に対象範囲と失敗時のフォールバックを定めたうえで、監視処理の変更を別タスクとして進める。

## 保存成果物の確認先

ダウンロード先の`PageRecorder/stock-fetch-diagnosis/<run-id>/`には、状態・URL別の`fetch.html`、`outerHTML.html`、`comparison.json`と、全体結果の`summary.json`、`判定結果の解説.md`、`summary.jsonの項目解説.md`、`README.md`が保存される。

`summary.json`は機械処理や詳細確認用の構造化データである。`判定結果の解説.md`は、最終判定の意味、次のアクション、状態別成功数、URL別のFetch／DOM結果を日本語で確認するための解説用ファイルである。`summary.jsonの項目解説.md`は、JSONの各項目値とその意味をコメント付きで読むためのファイルである。

popupの最終判定には、診断完了日時を日本時間で表示する。`summary.json`には同じ時刻を`diagnosedAt`（ISO 8601 / UTC）として保存する。

HTMLを外部の分析ツールへ渡す前に、Cookie、認証トークン、個人情報、注文情報を削除する。
