# requirements.md

## 🎯 目的

テストタブの A: single / A: multiple シナリオを、本番と同じ二層セッション経路で動かし、期待結果を自動で判定する。日産オンラインショップ以外のサイトでもテストできるようにする。移行後、テストタブからしか使われていない旧 `setInterval` 経路を削除する。

---

## 🎯 プロダクト概要

- **解決する課題**: テストタブの役割は「本番で監視する環境に最も近い状態で、シナリオに合う設定を固定し、自動化する」こと。しかし A: single / A: multiple のシナリオは、本番とは別の旧 `setInterval` 経路で動いており、テストの結果が本番の動きを保証しない。A: multiple は DevTools にコードを貼る手動確認が中心で、自動化も一部にとどまる。
- **対象ユーザー**: PageRecorder の開発者（テストタブで受け入れ確認・回帰確認を行う人）
- **成功指標**: テストタブのシナリオが本番と同じ処理経路を通り、結果が自動で判定される。旧経路のコードがなくなる。

---

## 📌 背景

- 本番の監視は、単一URL・複数URLとも二層セッション（storage を正本にした永続セッション、`startSingleMonitoring` の委譲先）で動く。
- 旧 `setInterval` 経路は2つあり、どちらもテストタブからしか使われていない（2026-10-23 確認）。
  1. 複数URL：`src/background/background.js` の `startMultipleMonitoring` 冒頭の分岐。requestId が `testMultiple_` で始まり、`useTwoTierSessions` がない場合（A: multiple 回帰シナリオ）
  2. 単一URL：`startSingleMonitoring` で `allowTestTiming` または `settings.autoTestRunId` がある場合（A: single のシナリオと自動判定）
- 本番経路で動き、自動で判定するテストはすでにある：「高頻度・複数URL」受け入れテスト（`startTwoTierAcceptanceTest`、`useTwoTierSessions: true`、`testOnly: "two_tier_acceptance"`）。
- 本番の設定範囲（`validateMonitoringModeSettings`）は、高頻度が間隔5〜20秒・時間60秒〜60分、長期が間隔30秒以上・時間30分〜8時間。既存シナリオの多くが使う「20秒 / 60秒」は高頻度の範囲内である。
- 関連する保留中タスク：
  - `261023-1332_multi-site-state-transition`：旧経路の判定を本番にそろえる応急処置。旧経路を削除すると不要になるため却下し、ブランチを削除した（2026-10-23 ユーザー承認。decisions.md D-001）。
  - `261023-1427_test-tab-site-selection`：テストタブで日産以外のサイトを選ぶ（Codex 実装 `372d355`、保留中）。日産以外のサイトでのテストは本タスクの要件に含めたため、その実装を取り込むかを design で決める。

## 👤 ユーザーストーリー

- as a PageRecorder の開発者
- I want テストタブのシナリオを押すだけで、本番と同じ処理で監視が動き、成功・失敗が自動で表示される
- so that テストの結果を本番の動きの根拠として使え、手作業の確認を減らせる

---

## 🧩 機能要件（仮）

1. A: single / A: multiple のシナリオを、本番と同じ二層セッションで開始する。
2. 各シナリオの期待結果（検知する／検知せず時間満了する／エラーになる）を自動で判定し、テストタブに表示する。受け入れテストの検証の仕組みを再利用する可能性がある。
3. 検知の再現は、既定では自動で行う。拡張が自動で在庫状態を変化させるコード（対象要素の文言変更）を入れて、在庫検知させる。popup のトグルで「自動」と「手動」を切り替えられるようにし、手動のときは、テストセッションだけに20秒の受付時間を設け、その間に利用者が DevTools でコードを実行して再現する。受付時間中であることはログでわかりやすく表示する（2026-10-23 ユーザー追加）。どちらの場合も結果の判定は自動で行う。
4. シナリオごとの固定設定（URL・セレクタ・キーワード・間隔・時間・保存設定）は維持する。
5. すべてのシナリオを移行したあと、旧 `setInterval` 経路（単一・複数）と、それ専用のテスト用分岐を削除する。
6. 本番の監視設定（`multiple_configs`、`multiple_common_settings`、単一URL監視の設定）は、テストの開始・終了で変更しない。
7. テストタブで、日産オンラインショップ以外のサイトも選んでテストできるようにする。サイトと監視条件は既存の設定（`ec-sites.json` の監視条件、`stock-fetch-diagnosis-sites.json` のサンプルURL）から作り、セレクタを推測で追加しない。
8. 「在庫なしから始める」シナリオは、選んだサイトに在庫ありと在庫なしの両方のサンプルURLがそろって初めて作成する。在庫なしサンプルがないサイトでは、そのシナリオを作らず、在庫なしサンプルの収集を促す文言をテストタブに表示する（2026-10-23 ユーザー決定）。在庫ありで始めるシナリオは、在庫ありサンプルだけで作成できる。
9. 監視条件が在庫なしページに対応していないサイト（在庫なしで監視要素そのものが消える）は、シナリオを作ったうえで本番と同じ判定で実行し、`element_not_found` なら失敗として理由（監視条件の見直しが必要）を表示する。本番で再入荷を検知できない問題をテストで見つけるため（2026-10-23 決定）。トイザらスの監視条件の修正は、ルート `chromeExtensions/plan/todo.md` に起票した別タスクで行う。
10. A: multiple は開始状態に対応する異なる商品URLを2件使う。同じ商品URLへのテスト用クエリ追加では代用しない。必要な状態のサンプルが2件未満のサイトでは開始せず、不足を表示する（2026-10-25 ユーザー決定）。
11. テストタブの結果カードには、実行開始日時と完了日時を表示する（2026-10-25 ユーザー決定）。

---

## ⚙️ 非機能要件

- 本番の監視の挙動を変えない（テスト用の分岐を本番の判定に混ぜない）。
- 自動再現は対象要素の文言変更だけにし、クリック・カート投入・フォーム送信などの不可逆な操作をしない。
- 新規ログは `logger` / `bgLog*` を使う。

---

## ✅ 受け入れ条件（Acceptance Criteria）（仮）

- [x] A: single / A: multiple のすべてのシナリオが、本番と同じ二層セッションで開始される（旧経路を通らない）。
- [x] 各シナリオの結果（成功・失敗と理由）が、手作業なしでテストタブに表示される。
- [x] popup のトグルで検知の再現を「自動」「手動」に切り替えられる。手動のときは、ログに受付時間中であることと残り秒数が表示され、20秒の受付時間内にコードを実行すると検知する。
- [x] 旧 `setInterval` 経路のコードが削除され、本番の単一・複数URL監視に回帰がない。
- [x] 既存の自動テストに回帰がなく、移行したシナリオと判定の自動テストを追加する。
- [x] 日産以外のサイトを選んでも、代表シナリオが本番と同じ経路・自動判定で動く。
- [x] 在庫なしサンプルがないサイトでは「在庫なしから始める」シナリオが作られず、在庫なしサンプルの収集を促す文言が表示される。
- [x] Chrome 手動確認で、代表シナリオ（出現・消失・即座検知・時間満了・エラー）が自動判定で成功する。

## 🚫 スコープ外（Out of Scope）

- B / C 定時監視のテスト
- 本番の監視ロジック（二層セッションの判定）の仕様変更

## 🚧 制約事項

- 監視設定の read / write は `MonitoringConfigManager` に集約する（`.claude/rules/chrome-extension-background.md`）。
- popup とのメッセージ契約を壊さない。
- 実サイト検証は不可逆な操作をしない（`chromeExtensions/.claude/rules/chrome-testing-rule.md`）。
