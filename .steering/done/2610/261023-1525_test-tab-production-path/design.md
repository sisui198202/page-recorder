# design.md

## 🎯 概要

テストタブの A: single / A: multiple シナリオを、既存の「高頻度・複数URL」受け入れテスト（`startTwoTierAcceptanceTest`）の仕組みに載せ替える。シナリオは本番と同じ二層セッションで開始し、基準取得後に拡張が自動で在庫状態（対象要素の文言）を変え、結果を自動で判定する。サイトは既存設定から選べるようにし、移行後に旧 `setInterval` 経路を削除する。

---

## 🧠 設計方針

- **土台は既存の受け入れテスト**：本番経路での開始（`runMultipleMonitoringStartConfigs` に `useTwoTierSessions: true`）、本番設定の退避と復元、通知の停止、基準取得後の自動 DOM 変更（content 側・background 側）、期待結果の判定（`hasTwoTierAcceptanceExpectedOutcomes`）がすでにある。これを一般化して全シナリオで使う。
- **本番の設定範囲を守る**：テスト用の短い間隔・時間（`allowTestTiming`）は使わない。全シナリオを高頻度モードの範囲内（間隔5秒・時間60秒）で動かす。
- **シナリオはデータで定義する**：今の「日産の定義を文字列置換して他サイト用にする」方式はやめ、シナリオごとに「どのサンプルで始めるか・どう変化させるか・何を期待するか」を持つデータにする。URL・セレクタ・キーワードは選んだサイトから入れる。
- **本番に近い値を使う**：出現系のシナリオも、テスト専用キーワードではなく、在庫なしサンプルとサイトの本当のキーワードを使う。

## 🧩 対応要件マッピング（最重要）

| 要件 | 設計での対応 |
|---|---|
| 1. 本番と同じ二層セッションで開始 | 全シナリオを `runMultipleMonitoringStartConfigs`（`useTwoTierSessions: true`）経由で開始 |
| 2. 自動判定・表示 | 受け入れテストの状態（`two_tier_acceptance_status`）を一般化し、期待結果に「検知」「満了」「セレクタエラー」を持たせる |
| 3. 自動で在庫状態を変化 | 受け入れテストの自動 DOM 変更を、出現（キーワード追記）と消失（キーワード削除）の両方に広げる |
| 4. 固定設定の維持 | シナリオ定義データに設定を固定する |
| 5. 旧経路の削除 | Phase 6 で削除（下記「削除対象」） |
| 6. 本番設定を変えない | 受け入れテストの退避・復元をそのまま使う |
| 7. 日産以外のサイト | サイト候補を既存設定から作り、選択をテストタブに追加 |
| 8. 在庫なしサンプルがないサイト | 在庫なし開始のシナリオを作らず、収集を促す文言を表示 |
| 9. 監視要素が消えるサイト | 実行して `selector_error` になったら、在庫なし開始シナリオでは「在庫なしページに監視要素がない（監視条件の見直しが必要）」と表示 |

## 🧩 シナリオ定義（移行後）

全シナリオ共通：高頻度モード、間隔5秒、時間60秒、保存はページソースとスクリーンショット。

### A: single（1タブ）

| ID | 開始ページ | 検知方法 | 即座検知 | 自動変化 | 期待結果 |
|---|---|---|---|---|---|
| appear | 在庫なし | 出現 | OFF | 基準取得後にキーワードを追記 | 検知 |
| disappear | 在庫あり | 消失 | OFF | 基準取得後にキーワードを削除 | 検知 |
| initial_detected | 在庫あり | 出現 | ON | なし | 検知（開始直後） |
| initial_not_detected | 在庫なし | 出現 | ON | なし | 満了 |
| element_not_found_check | 在庫あり（セレクタ `.page-recorder-test-valid-but-not-found`） | 出現 | OFF | なし | セレクタエラー |
| pending_error_check | 在庫あり（セレクタ `[`） | 出現 | OFF | なし | セレクタエラー |
| gmail_notification_check | 在庫なし | 出現 | OFF | キーワードを追記 | 検知＋Gmail 送信成功 |
| keyword_missing_check | ― | ― | ― | ― | 開始前のバリデーション（監視を開始しない。現状のまま） |
| chrome_notification_check | ― | ― | ― | ― | 共有 Chrome 通知の表示（監視を使わない。現状のまま） |

### A: multiple（開始状態に対応する異なる商品URL 2件）

| ID | 開始ページ | 即座検知 | 自動変化 | 期待結果 |
|---|---|---|---|---|
| baseline_two_urls | 在庫なし×2 | OFF | なし | 2件とも満了 |
| initial_detected_two_urls | 在庫あり×2 | ON | なし | 2件とも検知 |
| initial_not_detected_two_urls | 在庫なし×2 | ON | なし | 2件とも満了 |
| auto_appear_two_urls（旧 manual_appear_two_urls） | 在庫なし×2 | OFF | キーワードを追記 | 2件とも検知 |
| gmail_notification_one_url / two_urls | 在庫なし | OFF | キーワードを追記 | 検知＋Gmail 送信成功 |

- `duration_elapsed_during_reload_wait`（待機中に監視時間が満了する）は削除する。旧経路の「リロード後待機」専用の確認で、本番の二層セッションにはリロード後待機がないため。
- 既存の受け入れテスト（`high_frequency_*`、長期監視）はそのまま残す。
- 必要な開始状態のサンプルが2件未満のサイトでは、同一URLへ `ref=multi` を付けて複製せず、シナリオを開始不可にして不足を表示する。single と1件だけの Gmail シナリオは先頭のサンプルを使う。

### 在庫なしサンプルがないサイト

「開始ページ＝在庫なし」のシナリオは作らず、テストタブに「在庫なしサンプルがないため、このシナリオは使えません。`docs/在庫Fetch診断_サイト追加手順.md` の手順で在庫なしサンプルを追加してください」と表示する。

## 🧩 自動変化（基準取得後の DOM 変更）

既存の受け入れテストは、初回の確認（基準取得）のあと、`document.querySelector(selector)` の1件目にキーワードを追記している（`src/content/content.js` と `src/background/background.js` の両方）。これを次のように広げる。

| 変化 | 内容 |
|---|---|
| 出現（`detect_after_initial`、既存） | 一致した**すべての要素**の文言の末尾にキーワードを追記 |
| 消失（`disappear_after_initial`、新規） | 一致した**すべての要素**の文言からキーワードを削除 |

- すべての要素に適用する理由：トイザらスのように同じ状態のボタンが2つ（通常とスマホ用の固定ボタン）あると、1件目だけを変えても判定が変わらないため。
- 変えるのは文言だけで、クリック・属性・class は変えない。各要素に1回だけ適用する（既存の `data-page-recorder-two-tier-test-changed` 印を使う）。
- この処理は `testOnly` が付いたテストセッションでしか動かない（通常のセッションには `testOnly` がない）。

## 🧩 再現の自動・手動の切り替え（2026-10-23 追加）

- popup のテストタブに「検知の再現：自動 / 手動」のトグルを置く。既定は自動。選択は `localStorage` に保存する。
- 自動変化（出現・消失）があるシナリオだけで使う。自動変化のないシナリオ（満了・即座検知・エラー）では、トグルの値に関係なく同じ動きになることをテストタブに表示する。
- **自動**：上記「自動変化」のとおり、基準取得後に拡張が文言を変える。
- **手動**：拡張は文言を変えない。基準取得後の最初の読み込み直しの直後に、**20秒の受付時間**を設け、その間は確認を止める。利用者はこの間に、テストタブに表示されたコードを DevTools で実行する。受付時間が過ぎたら確認する。
  - 理由：本番の高頻度監視は読み込み直しの直後に確認し、次の読み込み直しまで待つ。受付時間がないと、手で変えた文言は確認より先に読み込み直しで消えてしまう。
  - 受付時間は `testOnly` 付きのテストセッションだけで動く。通常のセッションには影響しない。
  - 表示するコードは、選んだサイトのセレクタとキーワードから作る（出現：一致したすべての要素の末尾にキーワードを追記、消失：一致したすべての要素からキーワードを削除）。
- **受付時間のログ**（Service Worker Console。1行1責務、対象名を先頭に置く）:

| タイミング | ログ |
|---|---|
| 開始 | `🧪 [対象名] 手動変更の受付時間中です（残り20秒）。監視タブの DevTools でテストタブのコードを実行してください` |
| 10秒後 | `🧪 [対象名] 手動変更の受付時間中です（残り10秒）` |
| 15秒後 | `🧪 [対象名] 手動変更の受付時間中です（残り5秒）` |
| 終了 | `⏰ [対象名] 手動変更の受付時間が終わりました。これからキーワードを確認します` |

  - 開始・終了は警告色（`bgLogWarn`）で目立たせる。残り秒数は進捗ログ（`bgLogProgress`）で出す。
  - テストタブの結果欄にも「手動変更の受付時間中（残り◯秒）」を表示する。
- **判定はどちらも自動**：手動で受付時間内にコードを実行しなかった場合は、検知が起きずに満了するので「失敗：手動変更が確認できませんでした」と表示する。

## 🧩 判定と表示

- 受け入れテストの状態に、セッションごとの期待結果を持たせる：`expectedDetectionSessionIds`（既存）、`expectedExpirationSessionIds`（既存）、`expectedSelectorErrorSessionIds`（新規）。
- セッション終了理由（`deactivateSingleMonitoringSession` の `reason`）を記録する：`detected`（既存）、`expired`（既存）、`selector_error`（新規）。
- 全セッションが期待どおりに終われば成功。違えば失敗とし、理由を表示する。在庫なし開始のシナリオで `selector_error` になった場合は「在庫なしページに監視要素がない（監視条件の見直しが必要）」と表示する。
- Gmail シナリオは、既存の `getGmailNotificationAutoTestResult` で送信結果も判定に含める。
- テストタブの表示は、既存の受け入れテストの結果表示を使い、シナリオ名と選んだサイトを表示する。
- 結果カードには `startedAt` を「開始日時」、完了済みなら `completedAt` を「完了日時」として日本時間で表示する。実行中は開始日時だけを表示する。

## 🧩 サイト選択

- 候補の条件：`ec-sites.json` に監視条件がある（`pageRecorderMonitor` を優先、なければ `monitorProfiles`）、かつ `stock-fetch-diagnosis-sites.json` に在庫ありサンプルがある。在庫なしサンプルの有無も候補に持たせる。
- 保留中のサイト選択タスク（`feature/test-tab-site-selection`、`372d355`）の候補生成と選択UI・保存の考え方を参考にするが、cherry-pick はしない。そちらは文字列置換でシナリオを作る方式で、今回のデータ定義方式と混ざるため。
- 選択は popup の `localStorage` に保存し、既定は日産。

## 🧩 実装上の補足（Phase 1 調査後、2026-10-23）

- 受け入れテストの状態には、受け入れテスト専用の確認項目（確認の間隔、B/C アラームが変わらないこと、長期アラームなど）が多い。受け入れテストを壊さないよう、テストタブのシナリオは**別の `testOnly: "test_tab_scenario"` と別の状態キー**で管理し、本番設定の退避・復元、自動変化、Gmail 結果の確認などの部品を共有する。受け入れテストのコードは変えない。
- 単一URLシナリオは `startSingleMonitoring(settings, null, { persistConfig: false, monitoringScope: "single", testOnly, testRunId })` で開始する（本番の単一URL監視と同じ入口・同じ設定範囲チェック）。複数URLシナリオは `runMultipleMonitoringStartConfigs`（`useTwoTierSessions: true`）で開始する。
- 二層セッションの設定に、テスト時だけ `twoTierTestBehavior` と `gmailTestRunId` / `gmailTestConfigId` を渡す（今は `two_tier_acceptance` のときだけ `twoTierTestBehavior` を渡し、Gmail の実行IDは渡していない）。
- 高頻度監視の確認は content 側（`runHighFrequencySession`）で行うため、自動変化と手動の受付時間は content 側に置く。受付時間のログは、content から background へメッセージを送り、background が Service Worker のログに出す。

## ⚠️ 影響範囲

- テストタブの単一URLシナリオは、今は約15秒で終わるが、本番の範囲（最低60秒）に合わせるため「満了」を期待するシナリオは約60秒かかる。検知を期待するシナリオは検知した時点で終わる。
- 出現系のシナリオは在庫なしサンプルが必要になる。日産は在庫なしサンプル（6876）がある。
- 調査で見つけたこと（今回は対応しない）：本番の複数URL監視は二層セッションに `reloadWaitAfterReload`（リロード後待機）を渡しておらず、popup の「リロード後待機」は本番では効いていない。別途確認が必要なので `plan/todo.md` に起票する。

## 🧪 テスト方針

### 自動テスト（Jest、タイトルは日本語）

- シナリオ定義：サイトと在庫あり・なしサンプルから、各シナリオの設定（URL・セレクタ・キーワード・検知方法・即座検知・自動変化・期待結果）が作られる
- 在庫なしサンプルがないサイトでは、在庫なし開始のシナリオが作られない
- 判定：検知・満了・セレクタエラーの組み合わせで成功・失敗が正しく決まる。在庫なし開始で `selector_error` のときの理由
- 自動変化：出現は全要素に追記、消失は全要素から削除、2回目は変えない（content 側の関数を jsdom で確認）
- 手動モード：自動変化をしないこと、受付時間を設ける条件（`testOnly` 付き・手動・基準取得後の最初の読み込みだけ）、受付時間が20秒であること、手動用コードの生成、受付時間内に変化がないときの失敗理由
- 旧経路削除後、本番の単一・複数URL監視の既存テストに回帰がない

### 手動テスト（Chrome）

- セブンネットで、A: single の appear・disappear・initial_detected・initial_not_detected・element_not_found_check、A: multiple の auto_appear_two_urls・baseline_two_urls が、ボタンを押すだけで自動判定まで終わる。日産オンラインショップはメンテナンス中のため、復旧後の回帰確認へ保留する（2026-10-25 ユーザー決定）。
- 手動モードで、ログに受付時間中と残り秒数が出て、受付時間内のコード実行で検知し、実行しなければ「手動変更が確認できませんでした」で失敗する
- 本番の単一・複数URL監視（今すぐ開始）が今までどおり動く
- 不可逆な操作はしない

## 🚧 リスクと対策

| リスク | 対策 |
|---|---|
| 旧経路の削除で、本番が使っている関数まで消す | 削除前に呼び出し元を検索し、本番経路から呼ばれていないことを確認する。削除は独立したコミットにし、戻せるようにする |
