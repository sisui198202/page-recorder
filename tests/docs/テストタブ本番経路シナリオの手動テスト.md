# テストタブ本番経路シナリオの手動テスト

> テストタブの A: single / A: multiple シナリオが、本番と同じ二層セッションで動き、結果が自動で判定されることを Chrome 実機で確認する。

## 概要

- 対象: popup のテストタブの A: single / A: multiple シナリオ（監視を開始しない single 5 空キーワード・single 9 共有Chrome通知は対象外）
- 仕組み: 本番と同じ二層セッション（高頻度・間隔5秒・時間60秒）で監視を開始する。基準取得後に在庫状態を変え（自動または手動）、終了理由を期待結果と照合して判定する。本番の監視設定は開始前に退避し、終了時に復元する
- シナリオ一覧: [test-hub-scenario-catalog.md](./test-hub-scenario-catalog.md)
- 関連タスク: `.steering/261023-1525_test-tab-production-path/`

## 前提

- `chrome://extensions` で PageRecorder を再読み込みし、Service Worker Console を開いておく
- テストサイトには、在庫あり・在庫なしの両方のサンプルがあるサイトを使う。実在ECサイトへ接続しない場合は、先に `node tests/fake-ec/server.js` を起動し、**「【テスト専用】偽セブンネットショッピング（localhost）」** を選ぶ。詳細なURLと起動方法は [`tests/fake-ec/README.md`](../fake-ec/README.md) を参照する
- テスト前に、通常の複数URL監視の対象一覧と単一URL監視の設定を控えておく（終了後に変わっていないことを確認するため）
- 購入・カート投入・フォーム送信は行わない。在庫状態の変更は対象要素の文言だけで、ページを再読み込みすると元に戻る

## 共通の判定ログ

| ログ | 意味 |
|---|---|
| `🔄 [テストタブ] {シナリオ}（{サイト}）を本番と同じ経路で開始します` | テストの開始 |
| `🔄 [{対象名}] 基準取得後に在庫状態の文言を自動で変更しました` | 自動モードで在庫状態を変えた |
| `🧪 [{対象名}] 手動変更の受付時間中です（残り20秒）。…` | 手動モードの受付時間の開始（残り10秒・5秒も出る） |
| `⏰ [{対象名}] 手動変更の受付時間が終わりました。これからキーワードを確認します` | 受付時間の終了 |
| `✅ [テストタブ] {シナリオ}（{サイト}）の判定: 成功` / `❌ … 失敗` | 判定の結果 |

## T1: 出現を自動で再現して検知する（A: single 1）

目的:
- 在庫なしサンプルで始め、基準取得後に拡張がキーワードを追記したときに、本番と同じ判定で検知することを確認する

実行:
1. テストタブで「A: single」を選び、テストサイトを選ぶ
2. 検知の再現を「自動」にし、シナリオ「1. … 出現 …」を選ぶ
3. 実行内容の要約に「在庫なしサンプルで開始」と監視URLが表示されることを確認し、「テスト開始（自動判定）」を押す

期待結果:
- 在庫なしサンプルのタブが開き、`基準取得後に在庫状態の文言を自動で変更しました` のログが出る
- 結果欄が「成功」になり、`期待 検知 / 結果 検知` と表示される（十数秒）
- HTML とスクリーンショットが保存される

成功時の保証範囲:
- 選んだサイトの監視条件で、本番の二層セッションが「なし → あり」の変化を検知・保存・停止できること

失敗境界と保証されないこと:
- 結果が「在庫なしページに監視要素がない（監視条件の見直しが必要）」なら、そのサイトの監視条件は在庫なしページで使えない（本番でも再入荷を検知できない）。監視条件の見直しが必要
- 実際の在庫入荷による検知は保証しない（文言の変更で代替している）

---

## T2: 消失を自動で再現して検知する（A: single 2）

目的:
- 在庫ありサンプルで始め、基準取得後にキーワードを削除したときに消失として検知することを確認する

実行:
1. T1 と同じサイトで、シナリオ「2. … 消える …」を選んで「テスト開始（自動判定）」を押す

期待結果:
- 在庫ありサンプルのタブが開き、文言の自動変更のログのあと、結果欄が「成功」になる

成功時の保証範囲:
- 本番の二層セッションが「あり → なし」の変化を検知できること

失敗境界と保証されないこと:
- 実際の在庫切れによる検知は保証しない

---

## T3: 複数URLで出現を検知する（A: multiple 4）

目的:
- 複数URL監視でも、2件とも本番の経路で変化を検知することを確認する

実行:
1. 「A: multiple」を選び、シナリオ「4. 在庫なし2件で在庫状態を変えて検知する」を選んで開始する

期待結果:
- 異なる商品ページのタブが2つ開き、2件とも `期待 検知 / 結果 検知` で「成功」になる

成功時の保証範囲:
- 複数URL監視の二層セッションが、異なる2商品それぞれで変化を検知できること

失敗境界と保証されないこと:
- 2件より多い監視対象での動作は保証しない

ローカル偽サイトを使う場合:

- サーバーを起動したまま、テストサイトに **「【テスト専用】偽セブンネットショッピング（localhost）」** を選ぶ。
- 在庫ありサンプルが2件、在庫なしサンプルが3件登録されているため、A: multiple はシナリオ2を含め、開始状態に応じて異なる2 URLを自動選択して実行できる。
- 偽ページのカートボタンは送信・遷移しない。クリック確認をしても外部サービスや実在カートには影響しない。

---

## T4: 手動で在庫状態を変えて検知する（A: single 1、手動）

目的:
- 手動モードで、受付時間中であることがログでわかり、受付時間内のコード実行で検知することを確認する

実行:
1. 「A: single」・シナリオ1で、検知の再現を「手動」にする
2. テストタブに「手動で在庫状態を変えるコード」が表示されることを確認し、コピーする
3. 「テスト開始（自動判定）」を押す
4. Service Worker Console に `手動変更の受付時間中です（残り20秒）` が出たら、監視タブの DevTools Console でコードを実行する

期待結果:
- `残り20秒`・`残り10秒`・`残り5秒` と `受付時間が終わりました` のログが出る。テストタブの結果欄にも「手動変更の受付時間中（残り◯秒）」が表示される
- 受付時間の終了後に検知し、結果欄が「成功」になる

成功時の保証範囲:
- 手動モードの受付時間の表示と、手動の文言変更による検知

失敗境界と保証されないこと:
- 受付時間内にコードを実行しなかった場合は、時間満了で「手動変更が確認できませんでした」と表示される（これは期待どおりの失敗）

---

## T5: 本番の設定が変わっていないことを確認する

目的:
- テストの開始・終了で、本番の監視設定が変わらないことを確認する

実行:
1. T1〜T4 のあと、通常の複数URL監視の対象一覧と単一URL監視の設定を、前提で控えた内容と比べる

期待結果:
- どちらもテスト前と同じ

成功時の保証範囲:
- 実施したシナリオについて、本番の監視設定と Gmail 通知設定が復元されること

失敗境界と保証されないこと:
- テスト中に利用者が設定を変えた場合は、その変更も終了時にテスト前の状態へ戻る

---
