# 在庫取得方式診断改善計画

## 目的

指定した商品ページについて、既存の在庫監視条件（CSSセレクタとキーワード）が、JavaScript実行後のDOMだけでなく、PageRecorderのService Workerから取得するFetch HTMLでも使える可能性を可視化する。

本機能は監視設定を自動変更せず、商品ページHTML・outerHTML・比較結果を調査証跡として保存する。Fetch単独での在庫判定の本採用は、在庫あり・在庫なしの両状態を比較した後に決定する。

## 背景と方針

- 現行の定時監視は一時タブのDOMを `chrome.scripting` で取得する。Service Worker Fetchによる商品ページHTMLの在庫判定は未実装である。
- 既存のEC自動反映値は、手動調査またはChrome DevTools MCPで商品文脈を確認済みの比較基準として再利用する。
- popupだけでは、関連商品・非表示要素などを含むサイト固有の意味を確定できない。機械的な比較と、Codex/Claudeによる成果物分析を分離する。
- 日常の監視設定と入力を重複させないため、専用モードタブは増やさず、単一URL監視内に折りたたみ式の「取得方式診断」セクションを追加する。

## popupの設計

単一URL監視の「即座取得」付近に、常時表示の `取得方式診断（Fetch / DOM / API調査）` セクションを置く。

### ECサイト一括診断（追加）

- EC監視サイトの有効化が1件で、そのsite IDに状態別サンプルが同梱されている場合、`在庫あり・なしをまとめて診断`を主導線として表示する。未選択・複数選択・未登録では理由を表示して実行しない。
- 同梱サンプルは`site_capture/02_product_in_stock`と`03_product_out_of_stock`の`url.txt`を読む同期スクリプトで生成する。初期対象は日産オンラインショップだけであり、共有`ec-sites.json`は変更しない。
- 在庫ありはキーワード一致、在庫なしは同じセレクタに対するキーワード不一致を期待値として、全URLを順番に比較する。全件でFetchとDOMが期待どおりなら`FETCH_SUPPORTED`、DOMだけなら`DOM_ONLY`、それ以外は`NEEDS_REVIEW`とする。
- 状態・URLごとの`fetch.html`、`outerHTML.html`、`comparison.json`に加えて、同一run ID直下へ`summary.json`とREADMEを保存する。現在の任意URL単件診断は詳細操作として維持する。

- 取得元は既存の監視対象を使い、アクティブタブまたは指定URLを一時タブで開く方式を選べるようにする。
- 診断実行前に、画面上で観測した状態を `在庫あり`、`在庫なし`、`不明` から選択する。
- 判定対象はフォームに入力済みのセレクタ／キーワードを優先する。未入力の場合のみ、対象URLに一致する `ec-sites.json` の `pageRecorderMonitor`、次に既存の `inStock` / `inStockText` を使う。
- 実行結果には、取得URL・HTTP状態・Fetch/DOMそれぞれのセレクタ一致数・キーワード一致・暫定判定・次の調査手順を表示する。HTML本文はpopupへ返さない。
- 診断結果は既存の単一／複数監視設定、定時監視、通知を開始・変更しない。

## 取得・比較・保存

- backgroundはService Workerから商品ページをFetchし、リダイレクト後URL、HTTP状態、Content-Type、HTML本文を取得する。同じ対象ページから `document.documentElement.outerHTML` を取得する。
- 指定URL方式では一時タブを作成し、取得完了・失敗を問わず必ず閉じる。アクティブタブ方式では既存タブを閉じない。
- CSSセレクタの構文確認とFetch HTML／outerHTMLへの適用は、DOMを利用できるoffscreen文書で行う。比較結果は要約のみをbackground経由でpopupへ返す。
- 各実行に同一run IDを付け、`PageRecorder/stock-fetch-diagnosis/` 配下へ以下をダウンロードする。
  - `fetch.html`
  - `outerHTML.html`
  - `comparison.json`（観測状態、URL、時刻、解決した条件、HTTP情報、比較結果、判定コード）
  - `README.md`（2状態比較とAI投入前の認証情報・個人情報除去の注意）

## 暫定判定とAPI調査導線

| 判定コード                   | 条件                                                                    | popupでの案内                                                 |
| ---------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------- |
| `FETCH_COMPATIBLE_CANDIDATE` | Fetch HTMLとouterHTMLの双方で、セレクタとその内部キーワードを確認できた | 現在状態でFetch利用候補。反対の在庫状態も収集して最終確認する |
| `DOM_ONLY_CANDIDATE`         | outerHTMLでのみ条件を確認できた                                         | 商品ページHTML以外の在庫API調査が必要                         |
| `NO_MATCH`                   | 両HTMLで条件を確認できない                                              | 条件・バリエーション・表示タイミングを再確認する              |
| `INVALID_SELECTOR`           | CSSセレクタが無効                                                       | 監視条件を修正する                                            |
| `FETCH_ERROR`                | Service Worker Fetchが失敗した                                          | 取得条件・ログイン状態・サイト制限を確認する                  |

`DOM_ONLY_CANDIDATE`、`NO_MATCH`、`FETCH_ERROR` では「DevTools調査メモをダウンロード」を表示する。メモには対象URL、観測状態、既存条件、NetworkのFetch/XHRで確認する項目、保存済みrun IDを含める。

Network通信の自動収集は今回の対象外とする。`chrome.debugger` 権限の追加は強い権限警告、DevToolsとの競合、認証情報を含む通信内容の取り扱いを伴うためである。必要になった場合は、別タスクでHAR取込または任意権限による調査モードを検討する。

## AI分析ワークフロー

- 利用者は在庫あり・在庫なしを各1回以上、同じ商品・SKU／バリエーション・ログイン状態で診断する。
- 保存した2組のHTMLと `comparison.json`、必要なら手動保存したHARをCodex/Claudeの分析ワークフローへ渡す。
- 分析では対象商品の在庫を示す根拠、関連商品や非表示要素による誤検出、Fetch HTML採用可否、監視条件候補、在庫API候補と追加検証をレポートする。
- 拡張機能からCodex/Claude、外部サーバーへHTMLやHARを自動送信しない。

## 実装・検証順

1. backgroundの取得処理、offscreenのHTML比較処理、popupの診断セクションとメッセージ契約を追加する。
2. 成果物保存と、API調査メモのダウンロードを追加する。
3. ユニットテストで取得元別の後始末、Fetch失敗、無効セレクタ、Fetch/DOM双方一致、DOMのみ一致、条件未一致を確認する。
4. Chrome手動確認で、EC自動反映値のフォールバック、同一run IDの成果物保存、既存監視を変更しないことを確認する。
5. 在庫あり・なしの実ページ成果物を使い、AI分析ワークフローが最終判断を出せることを確認する。

## 完了条件

- popupでFetchとouterHTMLの比較結果および次の調査行動が確認できる。
- 取得証跡と比較JSONがローカルに保存される。
- 既存監視の設定・実行・通知境界に影響しない。
- Fetch単独の本採用が、単一状態の一致だけでは確定しないことをUIと成果物で明示する。
