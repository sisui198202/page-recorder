# ログ表記ガイド

## 目的

PageRecorder のログを読むときの前提と、今後ログ文言を揃えるときの運用指針をまとめる。

補足:
- 時刻プレフィックス自体の実装履歴は [実装済/log-timestamp-prefix.md](実装済/log-timestamp-prefix.md) を参照

## 現在のログ基盤

### background.js

`src/background/background.js` では、Service Worker 用のログ基盤が用意されている。

- `formatBgLogTimestamp()`
  - 先頭に `HH:mm:ss.SSS:` を付ける
- `writeBgConsole(method, message, ...args)`
  - 改行を含む文字列にも同じ時刻プレフィックスを付けて出力する
- `bgLogError` `bgLogWarn` `bgLogInfo` `bgLogDebug`
  - ログレベル判定を通して出力する。通常ログは重複抑止しない
- `bgLogProgress` `bgLogDiagnostic`
  - 明示した周期進捗・調査詳細だけを、対象scope付きで重複抑止して出力する
- `logger`
  - `error / warn / info / debug` の呼び出し口をまとめた薄いラッパー

実務上は、background 側の通常ログは `logger.*` または `bgLog*` を通す前提で読むのがよい。

## 重複抑止ポリシー

本文が同じという理由だけでログを抑止しない。`🛑 系統Aセッション停止完了` のような終端ログは、異なるsessionIdごとに必ず出力する。

| 分類 | 出力方法 | 重複抑止 |
| --- | --- | --- |
| 終端・結果 | `logger.*` / `bgLog*` | しない |
| 操作・設定 | `logger.*` / `bgLog*` | しない |
| 周期進捗 | `bgLogProgress` | 同一 `level + category + event + scope` の5秒以内のみ |
| 調査詳細 | `bgLogDiagnostic` | 同一 `level + category + event + scope` の5秒以内のみ |

- WARN / ERROR は分類を問わず抑止しない
- `scope` は対象を安定して識別できる値を使う。例: 周期リロードは `{ tabId, monitoringSystem }`、定時監視Tickは `{ siteId, scheduleIndex }`
- 周期ログを追加する場合は、本文ではなく `event` と `scope` に抑止対象を定義する
- 現在の周期進捗の適用箇所は、周期リロードの開始・DOM準備完了、定時監視Tick、周期リロード中の`contentScriptReady`受信

### monitoringConfigManager.js

`src/background/monitoringConfigManager.js` は `mcmLogger` を経由して background のログレベル設定へ接続する。

- 設定読込、Storage キー移行の確認、整合性確認、アラームの予約・解除の詳細は DEBUG
- 監視対象の追加・更新・削除、Excel 入出力の成功は INFO
- 補正・フォールバックは WARN、処理失敗は ERROR
- 旧来の詳細ログは互換層で `mcmLogger.debug` へ転送するため、INFO では表示されない

共有ライブラリ読込前の起動ログだけは、保存済みログレベルをまだ復元できないため例外として生の console を使う。対象ページへ `executeScript` で注入する診断ログも、Service Worker のログレベル設定の対象外である。

## 絵文字プレフィックスの推奨意味

現状コードで使われている絵文字は厳密な enum ではないが、読み手の解釈を次のように揃えると見やすい。

| 絵文字 | 意味 |
| --- | --- |
| `✅` | 成功、完了 |
| `❌` | エラー、失敗 |
| `⚠️` | 注意、継続可能な異常、フォールバック |
| `🔄` | 処理開始、切替、再試行、再読込 |
| `🎯` | 対象確定、主要イベント、検知 |
| `📸` | スクリーンショット保存 |
| `📄` | HTML やテキストなど本文系保存 |
| `💾` | 永続化、保存処理 |
| `🔒` | ロック、排他、実行抑止 |
| `🛑` | 停止、中断、監視終了判断 |
| `🚀` | 即時実行、初動、簡素化の強調 |
| `⏰` | スケジュール、時刻、監視ウィンドウ |

運用上の指針:
- 1ログで主役になる意味は 1 つに絞る
- `✅` と `❌`、`🔄` と `⏰` のような対になる表現は揃える
- 同じ系統のイベントでは先頭語彙を固定し、比較しやすくする
- 出現検知でセレクタからテキストを取得できたがキーワードが一致しない場合は、`ℹ️` の継続状態として出す。`❌` は要素未取得、セレクタ構文エラー、Content Script 実行失敗など、正常に監視を継続できない失敗だけに使う。

## 色付きログ

Chrome DevTools では `%c` と CSS を使って色付きログを出せる。

PageRecorder では `writeBgConsole()` 内で共有ライブラリ `LogHighlight.getPatterns()` を使い、正規表現パターンマッチで自動的に色分けを判定している。

### 色分けルール

共有 `log-highlight.js` の DEFAULT_PATTERNS と PageRecorder 固有パターン（`background.js` 初期化時に `LogHighlight.addPattern()` で追加）で判定する。

| 色 | 条件 |
| --- | --- |
| 赤（#ff4444） | `error` メソッド経由のログ、または `❌` で始まるメッセージ |
| 緑背景（#ccffcc） | 検知・在庫あり・`🎯` `⚡` `🎉` `🔄` `📸` `📄` `⏰` `🧪` `💾` で始まるメッセージ |
| 緑文字（#44bb44） | `✅` で始まる、または成功・完了・保存を含むメッセージ |
| 青（#4488ff） | 情報系・`[周期リロード]` を含むメッセージ |
| オレンジ（#ff6600） | `🛑` で始まる停止系メッセージ |
| なし | 上記に該当しないログ |

### 黄色になる代表的なパターン

- `⚡ 即座取得処理開始:` `🎉 即座取得処理完了`
- `🔄 単一監視開始処理開始:` `🔄 複数監視開始処理開始:`
- `✅ 個別監視開始完了` `✅ 単一監視設定保存完了` `🎯 複数監視開始結果:`
- `✅ キーワード出現検知！` `✅ キーワード消失検知！`
- `ℹ️ 監視キーワードは未出現（監視継続）` `ℹ️ キーワード存在確認`（単一監視の不一致判定）
- `🔄 [二層監視テスト] テストDOMを変化状態へ更新` `🎯 [二層監視テスト] 変化検知を確認`
- `🔄 Excel Import処理開始` `🔄 Excel Export処理開始`
- `✅ Excel Import完了` `✅ Excel Export完了`
- `📸 スクリーンショット保存完了` `📄 HTMLソース保存完了`
- `✅ 他拡張通知処理成功`
- `⏰ 定時監視ウィンドウアラームを予約しました`
- `⏰ 監視ウィンドウを開始しました` `⏰ 監視ウィンドウを終了しました`

定時監視の失敗は `❌` で始め、予約・開始・監視中の失敗だけを赤にする。正常終了は黄色のままとする。

A（単一URL監視）・B（単一サイト定時監視）・C（複数サイト定時監視）では、初回チェックと初回ベースライン後の準備リロードを除く、指定間隔ごとの再読込処理にだけ `[周期リロード]` を付与する。ページリロード開始、ページ準備待機、DOM状態確認、DOM準備完了、DOM待機ロック解除、`contentScriptReady` 受信を黄色にする。手動操作・通常のDOM待機・Cloudflare復旧リロード・エラー・他機能のDOM待機ログは対象外とする。

共通パターンは `shared/lib/logging/log-highlight.js` の `DEFAULT_PATTERNS` で管理されている。PageRecorder 固有パターンは `background.js` 初期化時に `LogHighlight.addPattern()` で追加される。

### 注意点

- 過剰配色は可読性を落とすため、パターンは重要イベントに限定する
- 新しいパターンを追加する場合は `log-highlight.js` の `DEFAULT_PATTERNS` または `background.js` の `addPattern()` を更新する
- 全拡張共通で使うパターンは `shared/lib/logging/log-highlight.js` を更新する

## 見やすさ改善の指針

- 先頭の語彙を統一する
  - 例: `監視開始` `監視終了` `保存完了` `保存失敗`
- 1ログ1責務にする
  - 開始通知、判定結果、保存結果を 1 行に詰め込みすぎない
- 主要 ID や対象名の位置を固定する
  - 例: `[siteId]` や `[schedule:n]` を先頭寄りに置く
- 成功 / 失敗 / 開始の対比を揃える
  - 例: `🔄 開始` → `✅ 完了` → `❌ 失敗`
- 冗長な反復ログを抑える
  - 同じ意味の読込成功ログが短時間に連続するならノイズ候補

`monitoringConfigManager.js` の設定読込・移行済み確認は DEBUG のため、通常の INFO 運用ではノイズにならない。

## console.group 系は有効か

`console.group()` と `console.groupCollapsed()` は有効だが、常用より限定利用が向いている。

有効な場面:
- 「複数監視開始 1 リクエスト」単位のまとまり
- 「1 監視対象の開始から保存完了まで」単位の長い処理
- Cloudflare 回復、baseline 取得、複数保存処理のように関連ログが多い場面

常用を勧めない理由:
- Service Worker ログでは展開操作が増える
- 重要ログまで折りたたまれると通常運用の追跡が遅くなる
- フラットなログ検索との相性が下がる

現状コードでは `console.group` 系は未使用であり、導入するなら次の使い分けが妥当。

- 通常運用:
  - フラットな重要ログ中心
- 詳細調査:
  - `group` + `debug` ログで一連処理をまとめる

## 推奨パターン

通常の運用ログでは、次を優先する。

- `logger` / `bgLog*` 経由で出す
- 先頭に絵文字 + 対象 ID + 動詞を置く
- 重要な保存結果、開始終了、異常系だけを残す

詳細な調査ログでは、次を追加で使う。

- `debug` レベル
- 必要に応じて `console.groupCollapsed`
- オブジェクト引数で補足情報を出す

## この文書の範囲外

- `popup.js` や `content.js` のログ整理
- popup / content script / 対象ページ注入コードの `console.*` 統一
- 分類対象の全ログを一括で専用ヘルパーへ移行すること

必要になった場合は、別タスクとして設計してから進める。
