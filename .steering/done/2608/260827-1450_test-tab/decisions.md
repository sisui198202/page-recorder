# 🧠 decisions.md

## 🎯 目的

設計・仕様・実装に関する意思決定と、その理由を記録する。

---

## 📌 使い方

- 「なぜそうしたか」を必ず残す
- 後から見て判断理由が分かる状態にする
- 却下案も含めて記録する

---

### D-001: シナリオ3 `initial_detected` のログは成功として記録する

- **決定内容**:
  - 2026-08-28 のシナリオ3ログは、`initial_detected` の期待挙動どおりに「初回判定で在庫ありを検知し、保存後に監視完了した成功ケース」として扱う
  - 設定読込ログ多発と storage キー移行ログは、今回の判定では未調査ノイズとして分離し、失敗理由には含めない

- **背景**:
  - popup `テスト` タブのシナリオ3は、`initialKeywordDetection: true` と `detectMode: appear` により、開始直後の一致判定を確認するための固定シナリオである
  - 提示ログには、初回判定成功、保存系成功、`completed` 設定、定期監視スキップ、クリーンアップ完了までの一連の成功ログが揃っていた

- **検討した選択肢**:
  - 案A: 設定読込ログ多発を異常とみなし、シナリオ3全体を失敗扱いにする
  - 案B: シナリオ3は成功とし、読込ログ多発は別論点として保留する

- **採用理由**:
  - `changeMode: test` 完了後に、`初回チェック実行 [出現検知モード]`、`Content Script実行結果 ... detected: true`、`キーワード出現検知`、保存完了、`completed状態設定完了`、`即座検知で監視完了 → 定期監視スキップ` が揃っており、シナリオの合格条件を満たしている
  - `hasMonitoringConfig: false` / `hasMonitoring_config: true` に対して「既に移行済み」と一貫したログが出た後も、設定保存・モード変更・監視開始が成立している

- **却下理由**:
  - 案Aは、成功経路の完了ログ群と矛盾する
  - 今回の目的は不具合調査ではなく、提示ログの判定方針確定であり、ノイズ最適化を同じ結論に混ぜると記録が曖昧になる

- **影響範囲**:
  - `.steering/260827-1450_test-tab/tasks.md` の手動テスト記録
  - `tests/docs/README.md` のシナリオ3確認観点
  - 今後の回帰確認メモ

- **関連ドキュメント**:
  - requirements.md: popup `テスト` タブの手動テスト導線整理
  - design.md: `initial_detected` シナリオ定義
  - tasks.md: 2026-08-28 手動テスト記録

- **ステータス**:
  - [x] 確定
  - [ ] 見直し予定
  - [ ] 廃止

- **備考**:
  - 未調査ノイズは「設定読込ログの回数最適化要否」と「同一シナリオ再実行時の `single_config_backup` / モード切替回帰確認」に限定して別管理する

### D-003: シナリオ5 `pending_error_check` のログは異常系成功として記録する

- **決定内容**:
  - 2026-08-28 のシナリオ5ログは、`pending_error_check` の現在実装どおりに「無効セレクタで `error` を検出し、監視停止まで安全に完了した異常系成功ケース」として扱う
  - `monitoringConfigManager.js:100` の読込ログ多発、storage キー移行ログ、`DOM準備待機タイムアウト`、ページ側 DevTools 警告は今回の成功判定とは分けて扱う
  - シナリオ名に `pending` を含む一方で、実挙動は `error` 停止確認である点は別論点として残す

- **背景**:
  - popup `テスト` タブのシナリオ5は、在庫ありページに存在しないセレクタ `.page-recorder-test-invalid-selector` を入れて、UI や状態管理を壊さず `error` 系の切り分けを行う固定シナリオである
  - 提示ログには、基準保存成功、定期監視開始、無効セレクタの `querySelectorAll(...).length = 0`、Content Script と Background のセレクタエラー、interval 削除、実行ロック解除、監視停止までの一連の期待ログが揃っていた

- **検討した選択肢**:
  - 案A: セレクタエラー停止を失敗扱いにする
  - 案B: 異常系シナリオとしては成功とし、`error` 検出と停止完了を合格条件にする

- **採用理由**:
  - シナリオ5の目的は「成功通知」ではなく、無効セレクタ時に `error` を正しく検出し、`getStatus` 正規化や監視状態を壊さず停止できるかの確認である
  - `❌ [Content Script] セレクタエラー`、`❌ [Background] セレクタエラー検出 - 監視を停止します`、`setInterval削除完了`、`実行ロック解除完了`、`🚨 セレクタエラーのため監視を停止しました` が揃っており、異常系の完了条件を満たしている

- **却下理由**:
  - 案Aは、異常系テストの期待結果そのものを否定する
  - ページ側の CSP 警告や広告系通信エラーは、今回のセレクタエラー判定とは独立している

- **影響範囲**:
  - `.steering/260827-1450_test-tab/tasks.md` の手動テスト記録
  - `tests/docs/README.md` のシナリオ5確認観点
  - 今後のシナリオ命名見直しメモ

- **関連ドキュメント**:
  - requirements.md: popup `テスト` タブの手動テスト導線整理
  - design.md: `pending_error_check` シナリオ定義
  - tasks.md: 2026-08-28 手動テスト記録

- **ステータス**:

- **備考**:

## 📝 運用ルール

- Decisionは必ずID（D-XXX）で管理する
- 小さな判断でも記録してよい
- 後から変更された場合は履歴を残す
- 過去のDecisionは削除しない
