# requirements — AEON 定時 監視ウィンドウ（リロード監視）

## ビジネス目的

イオンスタイルオンライン（AEON）の指定検索一覧において、**競合より早く新規掲載を検知**し、連携拡張の自動購入フロー（カートイン〜購入手続き）へ渡す。

対象例: ポケモンカード関連の検索結果一覧。入荷・新規掲載が **12:00 / 13:00 / 14:00 前後** に集中する傾向があるため、**入荷予想時刻の前後で張り付き監視**する。

---

## 背景

- 1日1回・定点1回の確認では、入荷直後を逃しやすい
- 一覧ページの DOM は `/product/0/P-...` 形式が主で、旧 `ProductDetail.aspx` セレクタでは検知できない
- 検知後は PageRecorder が他拡張（例: discord_post_url_monitor）へ URL を渡し、AEON URL トリガーで購入処理を行う

---

## ユーザーストーリー

- **As a** 拡張機能利用者
- **I want** 入荷が予想される時間帯の前から一覧をリロードしながら監視したい
- **So that** 新規商品 URL が載った瞬間に通知され、誰より早く購入フローに入れる

---

## 検知の定義

### 主シグナル（本フェーズ）

| 項目 | 内容 |
|------|------|
| 対象ページ | popup で指定した AEON 検索結果一覧 URL |
| 比較元 | 監視セッション開始時点の baseline（`scheduledStockSnapshots` の当該 URL） |
| 検知条件 | 現在の一覧から取得した URL 集合に対し、**baseline に無い `/product/0/P-...` が1件以上**（`newUrls`） |
| 検知後 | `newUrls` を最大5件まで他拡張へ通知。監視セッションは終了 |

代表 URL の取得: `li.product__item .product__item--name a[href*="/product/0/P-"]`（商品1件あたり1 URL）

### 補助情報（参考・主判定ではない）

- 一覧本文の「対象アイテム：N件」件数（`count`）はログ・通知メッセージ用。URL 差分が空のときは通知対象にしない

### 本フェーズのスコープ外（検知）

| ケース | 理由 |
|--------|------|
| **同一商品 URL の再入荷**（一覧に URL は残ったまま商品ページだけ在庫復活） | 商品ページ在庫監視は別機能 |
| **2ページ目以降のみへの掲載** | 現状は1ページ目 DOM に載った分のみ取得（件数表示と URL 件数が一致しないことがある） |
| **12 / 13 / 14時を別ウィンドウで自動切替** | 1組の開始・終了のみ。運用で長い帯を指定する |

---

## 機能要件

### 実装済み（本フェーズ）

1. popup で **監視開始時刻**・**監視終了時刻**・**リロード間隔（秒）** を指定できる（5〜300秒）
2. 毎日、**開始時刻**に監視セッションを開始する（`chrome.alarms`）
3. **終了時刻**まで、新規 URL が無ければ一覧タブを **リロード** して再チェックする
4. **新規 URL** を検知したら `newUrls` を他拡張へ通知し、監視を終了する
5. 終了時刻に達して未検知の場合は監視を終了し、スナップショットを更新する（翌日 baseline 用）
6. 監視中は **セッション開始時の baseline** と比較し、ループ毎に baseline を上書きしない
7. baseline の URL が空の場合、初回スナップショットをセッション内 baseline に設定してからリロード監視を続ける

### 運用要件（設定上の推奨・機能追加ではない）

ユーザーが popup で調整する。実装は1ウィンドウのみ。

| 狙い | 監視開始 | 監視終了 | リロード間隔の目安 |
|------|----------|----------|-------------------|
| **12時台のみ** | 11:55〜11:57 | 12:08〜12:10 | 5〜10秒（負荷・タイムアウトに注意） |
| **12〜14時を広く** | 11:55 | 14:10 | 15〜30秒 |
| 保守的（負荷軽減） | 11:57 | 12:05 | 30秒 |

13:00 / 14:00 の波だけを別途見る場合は、**日替わりで開始・終了を切り替える**か、**長い1ウィンドウ**でカバーする。

## 非機能要件

### 信頼性・実装制約

- Manifest V3 のため、ポーリングは `chrome.alarms`（`stockWatchTick`）で継続する
- 同時に複数の監視セッションを走らせない
- DOM 準備タイムアウトが発生しても、取得できた範囲で差分判定を続行する

### 遅延目標（プロダクト目標・ベストエフォート）

| 段階 | 目標 | 備考 |
|------|------|------|
| **検知** | 一覧への新規 URL 掲載から **≤15秒** 以内（理想 **≤10秒**） | リロード間隔・ページ読込・SW 起動に依存 |
| **通知** | 検知から **≤5秒** 以内に他拡張へ `PAGE_RECORDER_STOCK_DETECTED` | PageRecorder 側の処理 |
| **購入完了** | 本リポジトリのスコープ外 | 連携拡張・ログイン・在庫切れに依存 |

間隔を **5秒** に短縮すると検知は速くなるが、AEON 負荷・タイムアウト・ブラウザ負荷が増える。

### 連携前提

- popup: **他拡張へ通知する** ON、正しい **通知先拡張機能 ID**
- 連携先: URL 監視（AEON）ON、自動カート（イオン）ON

---

## スコープ外（Out of Scope）

- 購入完了・決済成功の保証
- CAPTCHA / 抽選落選 / 購入制限の回避
- AEON 側レート制限・BAN 対策の保証
- 複数監視ウィンドウの同日自動スケジュール（将来検討）
- 商品詳細ページのみの在庫復活検知
- 競合他社より必ず早いことの保証（環境・間隔・回線に依存）

---

## 受け入れ条件（Acceptance Criteria）

### 設定・起動

- [ ] popup で監視開始・終了・リロード間隔を保存し、`monitoring_config` に反映される
- [ ] 開始時刻に監視セッションが `active: true` で開始する
- [ ] 終了時刻まで `stockWatchTick` によりリロードループが継続する

### 検知・通知

- [ ] 一覧の代表 URL が baseline より増えた場合、`newUrls` に `/product/0/P-...` が含まれる
- [ ] `newUrls` がある場合のみ他拡張へ通知し、誤って一覧 URL のみを渡さない
- [ ] 手動テスト（baseline を1件減らす）でループ内通知が1回出る

### 運用

- [ ] 12時台前後の推奨設定（11:57〜12:10、間隔5〜30秒）で手動または定時実行できる
- [ ] 手順は `tests/aeon-scheduled-stock-check-sw-manual.md` に記載されている

## 将来検討（次フェーズ候補）

- 同日 **複数監視ウィンドウ**（12時 / 13時 / 14時プリセット）
- **件数増 + URL 差分** の複合判定
- 一覧 **全件取得**（ページネーション・件数と URL の整合）
- 監視失敗・SW 停止時の **明示通知**
- 商品ページ **在庫テキスト** 監視との併用
